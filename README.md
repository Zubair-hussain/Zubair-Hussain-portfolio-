## ✨ Key Features

- **🎮 Immersive 3D Hero Section:** Built utilizing React Three Fiber (`@react-three/fiber`) and Drei to showcase a custom optimized GLB avatar with interactive hovering, orbiting, and rim-lighting effects.
- **⚡ Next.js 16 Server Components:** Optimized SSR and dynamic imports with automatic suspense boundaries.
- **🌍 Full i18n & RTL Support:** English, Urdu, Spanish, Hindi, Russian, and German interfaces, including Urdu RTL support.
- **🎭 Theme System:** Dark and light themes using Tailwind CSS with locally saved preferences and zero theme flash.
- **📱 100% Fully Responsive Layout:** Mobile-first approach using Framer Motion (`framer-motion`) and Lenis for buttery-smooth native scrolling experience.
- **📬 Integrated Contact System:** Ready-built integration for Resend / EmailJS to receive client communications directly.

## 🚀 Getting Started Locally

Follow these steps to preview and modify the portfolio source code on your local machine.

### 1. Clone & Install Dependencies

Use **Node.js 22+** and npm 10.5+. Current Cloudflare, Wrangler, testing, and 3D-control packages require Node 22, so local development and every GitHub Actions workflow use the same runtime generation.

```bash
git clone https://github.com/Zubair-Hussain/Zubair-Hussain-portfolio-.git
cd Zubair-Hussain-portfolio-
npm ci
```

### 2. Environment Variables configuration

Copy the `.env.local.example` structure to setup your secret keys.

```bash
cp .env.local.example .env.local
```

Important variables:

| Variable | Visibility | Purpose |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | Public | Canonical site origin |
| `BLOGGER_API_KEY` | Server/build only | Optional official Blogger API access |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | Public | Renders the hire-form challenge |
| `TURNSTILE_SECRET_KEY` | Server only | Verifies challenge responses |
| `EMAILJS_SERVICE_ID` | Server | EmailJS service identifier |
| `EMAILJS_TEMPLATE_ID` | Server | Hiring email template |
| `EMAILJS_PUBLIC_KEY` | Server route | EmailJS public API identifier |
| `SCHEDULE_JWT_SECRET` | Server only | Signs short-lived schedule tracking tokens |
| `NEXT_PUBLIC_FIREBASE_*` | Public | Firebase Web SDK project configuration |

Never prefix Blogger, Turnstile-secret, schedule-secret, Cloudflare, or SMTP
credentials with `NEXT_PUBLIC_`.
Configure the Turnstile and EmailJS values shown in `.env.local.example` to
test the secure hire form. Missing Turnstile configuration fails closed instead
of using an always-passing development key.

### 3. Run the Development Server

Execute the Next.js development server.

```bash
npm run dev
```

Visit [http://localhost:3000](http://localhost:3000) to view the development build. The app will automatically hot-reload upon saving any changes.

The `predev` lifecycle hook refreshes the Blogger snapshot. It can also be run
independently:

```bash
npm run blog:generate
```

### Quality and production commands

```bash
npm run type-check   # TypeScript validation without emitting files
npm test             # Complete Vitest suite
npm run lint         # ESLint
npm run build        # Blogger snapshot + Next.js production build
npm run cf-build     # Blogger snapshot + OpenNext Cloudflare build
npm run deploy       # Generate, build, and deploy to Cloudflare
```

## 📊 Performance (Lighthouse)

The application hits multiple performance ceilings through strategic build steps:
- **Image Optimization:** Utilizes `next/image` with lazy loading on all non-critical images.
- **Asset Minification:** 3D GLB Models are pipeline compressed into chunked Draco / WebP payloads.
- **Zero-FOUC Theming:** Synchronous local storage reading prevents any flashes during theme paints.

## Blogger and SEO

- Blogger is the CMS, but it is never queried during ordinary page requests. `npm run blog:generate` fetches, normalizes, and sanitizes the complete feed once into `src/generated/blog-posts.json` before a build.
- The homepage, `/blog`, every `/blog/[slug]` route, `/api/articles`, and `sitemap.xml` read the same generated snapshot. Article routes use `generateStaticParams()` with dynamic fallback disabled, so Cloudflare serves real static HTML.
- The homepage receives only six lightweight records (`slug`, title, excerpt, ISO date, and tags); full article bodies stay out of its React payload.
- Authored Blogger descriptions and keywords are reused for the local page's meta, Open Graph, Twitter, and BlogPosting data.
- Full article bodies are sanitized into one clean primary-language article; Blogger-only scripts, controls, authoring notes, and duplicate translation panes are removed.
- `.github/workflows/blogger-rebuild.yml` fingerprints Blogger every 30 minutes. A change regenerates all static pages, updates the archive/homepage/sitemap together, runs checks, and deploys to Cloudflare.
- The official Blogger API is used when `BLOGGER_API_KEY` is configured; public Blogger feeds remain automatic fallbacks.

The Blogger blog ID is fixed in `src/lib/blog.ts`. Only the optional `BLOGGER_API_KEY` needs environment configuration, and it must remain server-side.

## Automated security and production audits

### Cloudflare security-audit-skill snapshot

The repository was reviewed with Cloudflare's open-source
[`security-audit-skill`](https://github.com/cloudflare/security-audit-skill).
The 2026-09-25 run mapped ten trust-boundary units covering APIs, Blogger HTML,
Firebase, EmailJS/Turnstile, GitHub Actions, and Cloudflare deployment.

- Confirmed vulnerabilities: **0** (none completed the required independent validation)
- Deferred coverage units: **10**
- Highest-priority source leads: privileged `workflow_run` ref handling, regex HTML sanitization, public cost-bearing APIs, and client-only anti-abuse
- Immediate hardening applied: trusted deploy-only audit trigger, non-persisted checkout credentials, server-side Turnstile verification, bounded contact fields without PII logging, and Calendly host allowlisting
- Audit status: **incomplete**, because the independent audit-agent quota was exhausted and Cloudflare's validators require POSIX no-follow/nonblocking file guarantees unavailable on this Windows host

Read the checked-in [Cloudflare source-audit report](./docs/cloudflare-security-audit-2026-09-25.md).

To reproduce or resume the audit, follow the
[project-local audit toolkit guide](./.audit-tools/README.md). It includes the
upstream clone command, sandbox requirements, artifact layout, validator
commands, and resume rules. The upstream checkout remains ignored so a nested
third-party repository is not committed.

The `Security and Production Audit` workflow runs after successful trusted deployments and every Thursday at 03:15 UTC. It performs dependency auditing, TypeScript validation, CodeQL analysis, production URL and sitemap checks, and Lighthouse audits for the homepage and blog. Pull-request build revisions are intentionally excluded from this privileged follow-up workflow.

Failures open or update a GitHub issue so repository watchers are notified. Lighthouse reports are retained as downloadable artifacts for 30 days. Configure the optional `PRODUCTION_URL` repository variable when moving from the Workers URL to a custom domain.

See **[Automated security and production audits](./docs/automated-security-audits.md)** for setup, scheduling, checks, and notification behavior.

The separate **Monthly Portfolio Audit** checks every sitemap URL for crawlability, redirects, canonical tags, metadata, and structured data. See **[Monthly portfolio audit](./docs/monthly-indexing-audit.md)** for details.

The **New Blog SEO Readiness Audit** also detects new Blogger URLs hourly, validates their SEO metadata, and emails a readiness report. It does not submit URLs or request indexing.

For GitHub-triggered production deployments, use the **Deploy to Cloudflare**
workflow. It runs type checks and tests, executes `npm run deploy`, and records
a GitHub `production` deployment when Cloudflare finishes. The workflow runs on
pushes to `_prod` and can also be started manually from the Actions tab.

Configure these repository secrets before using the deployment workflow:
`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Configure the optional
`PRODUCTION_URL` repository variable when moving from the Workers URL to a
custom domain.

The hire form additionally requires `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and the
server-only `TURNSTILE_SECRET_KEY`. Configure `EMAILJS_SERVICE_ID`,
`EMAILJS_TEMPLATE_ID`, and `EMAILJS_PUBLIC_KEY` as Worker variables; legacy
`NEXT_PUBLIC_EMAILJS_*` names remain supported during migration.

For Cloudflare Workers Builds, use `npm run cf-build` as the build command and
`npm run cf-deploy` as the deploy command. A plain `next build` does not create
the `.open-next/worker.js` Worker entry point required by Wrangler.

Add `NEXT_PUBLIC_FIREBASE_*` under **Settings > Variables & Secrets** for the
Worker runtime. The Testimonials client retrieves this intentionally public
Firebase Web SDK configuration from `/api/firebase-config`, so the values do
not also need to be duplicated under Build Variables and Secrets. Wrangler is
configured with `keep_vars = true` to preserve dashboard-managed variables.

### Version policy

Node 22 is now the declared baseline because current Cloudflare, Wrangler,
testing, and 3D-control dependencies require it. Compatible updates stay within
the existing major release so the application receives fixes without silently
changing framework contracts. Major upgrades are isolated migrations:

- Tailwind 4 requires CSS/config migration.
- Zod 4 requires API error/type review.
- ESLint 10 requires plugin compatibility review.
- Framer Motion 13 requires animation and bundle review.
- React Spring 10 requires 3D motion verification.
- Postprocessing 3 requires visual regression testing.
- Vitest 5 requires test-runner and coverage migration.

Every upgrade must pass type checking, all tests, coverage thresholds, lint,
Next build, OpenNext build, and a visual preview before production deployment.
